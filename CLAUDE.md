# Hoops Playbook

Animated basketball playbook that teaches young kids basic plays, hosted on GitHub Pages. Static site, no build step
and no dependencies: `index.html` + `css/styles.css` + ES modules in `js/`, with each play as a JSON file in `plays/`,
plus a play editor (`editor.html`). The deploy adds one generated file, `plays/bundle.json` (see Loading).
The only external request is Google Fonts (Fredoka). Originally a single-file page built in a claude.ai chat.

Work still to do (full court, steals, editor tests and more) is listed in `PENDING.md`.

## Commands

- `npm start`: serve the site at http://localhost:8000 (`tools/serve.js`). Needed because the page fetches plays, which browsers block on `file://`. It builds `/plays/bundle.json` fresh on every request, so play edits show up on reload. The Browser pane preview config is `.claude/launch.json` (name `hoops`).
- `npm run build`: check every play, the learning paths and the glossary, and rewrite `plays/index.json` (`tools/build.js`). Run it after adding, renaming or removing a play. Exits 1 on any error and leaves `index.json` alone. `node tools/build.js --bundle` also writes `plays/bundle.json`; only the deploy needs that.
- `npm test`: unit tests in `tests/` (`node --test`, no dependencies) for `playbook.js` and `court.js`. They also check that every play passes `checkPlay`/`lintPlay`, that `index.json` lists every play, that `formatPlay` reproduces every play file byte for byte, that `paths.json` and `glossary.json` pass their checks, that the bundle matches the files, and that `sw.js` saves every page, script and stylesheet.
- Deploy: `.github/workflows/pages.yml` runs the tests and `node tools/build.js --bundle` on push to `main` and publishes the repo root (with the new bundle) to Pages. PRs only run the tests and checks.

## Layout

- `js/playbook.js`: pure logic, no DOM. `SPOTS`, `checkPlay` (returns a list of problems), `resolvePlay` (fills in every player's position per frame as `res`/`ctrl`, plus `handoffT[k]`, the moment of closest approach in a handoff step, `missAt[k]`, where a missed shot bounces to: 40 units off the rim toward the next frame's rebounder, and `hand[k]`, which side of the holder the ball is on at the end of frame k: 1 right, -1 left), `posAt`, `isThree`, `ballKind`/`startHolder`/`endHolder` (what the ball does; who has it as a step starts and ends, `null` around a miss), `askList`, `lintPlay` (the checks that need a resolved play; returns `{ errors, warnings }`), `checkPaths` (problems with `plays/paths.json`), `checkGlossary`/`lookUp` (the glossary: problems, and the entries for a list of words, matched by `word` or `also` after `normalize`), `DATA_FILES` (the files in `plays/` that aren't plays: `index`, `paths`, `glossary`, `bundle`), `formatPlay` (a play as the exact text of its file: canonical key order, one field per line, values inline), search (`searchPlays`, weighted word-prefix matching over name > tags > idea > why/tryit > captions). Imported by the page, the editor, `tools/build.js` and the tests, so keep it browser- and Node-safe.
- `js/court.js`: SVG drawing as strings, no DOM: `courtBackground` (the page inserts it into `#court` at startup), `courtView`, `stepAt`, `stepPaths`/`pathsUpTo` (movement lines, with an optional followed player), `ballState` (ground spot, height, scale and holder for every ball action), `screensAt`/`wallsSVG`, `bubblesAt`/`bubblesSVG`, `playerSVG`, and `renderCourt(play, p)`, a complete still `<svg>` at timeline position p used by the print sheet and the editor.
- Loading: `js/library.js` (`loadLibrary()`, shared by the page and the editor) fetches `plays/bundle.json`, which is `{ index, plays: { id: play }, problems, paths, glossary }` built by `tools/bundle.js`. If there's no bundle (another static server, or a bundle that failed), it falls back to `plays/index.json`, each `plays/<id>.json`, `paths.json` and `glossary.json`. The bundle is never committed (`.gitignore`): the deploy writes it after the checks pass, and `serve.js` builds it live. Nothing in it is trusted more than the files: the page checks every play the same way either way.
- Offline: `sw.js` (site root, so its scope is the whole site) is a service worker that `saveForOffline()` in `library.js` registers from both pages. It skips localhost unless the address has `?offline`, so it never sticks to other projects on port 8000. On install it saves `SHELL` (every page, script and stylesheet; `tests/offline.test.js` fails if one is missing) and `plays/bundle.json` (or `index.json` plus every play file when there's no bundle). Same-origin requests are network-first: the network's answer is saved and used if it comes within 4 s, else the saved copy, and a navigation that was never saved gets the saved home page. Google Fonts are saved-first in their own cache. To make visitors throw away the old copy, change `CACHE`. `#offline` in the library panel shows while `navigator.onLine` is false.
- `js/app.js`: the page. Gets the library from `loadLibrary()`; a play that fails to load or fails `checkPlay` is skipped with a console warning. Library UI (search box, level filter, play list, tag buttons, copy-link), URL hash routing (`#<id>` selects a play; picking a play updates the hash with `replaceState`, but the first load never rewrites the URL, so the bare site URL stays bare; "Copy link" builds the link from the current play, not the address bar), the court animation, "Who's open?" mode, read aloud, follow, and the print sheet.
- Learning paths: `plays/paths.json` is a list of `{ id, name, emoji, about, plays }`, where `plays` are play ids in the order to learn them (a play can be in several paths, or none). `app.js` loads it after the plays and fills the "Path" select in the library; a missing or broken file just hides the select. Picking a path clears the search and level, selects the path's first play, and lists only its plays in path order ("Play 2 · Easy"); search and level then filter within the path, and "Next play" walks it ("You finished the … path!"). A tag button or "Show all plays" goes back to all plays. The path isn't in the URL.
- Glossary: `plays/glossary.json` is a list of `{ word, also?, means }`; `also` holds other names (tags like `blob`, `ato`, `pick`). It shows up three ways: "Words to know" under each play (its tags looked up with `lookUp`, also on the print sheet), a word card under the search box when the whole query is a glossary word (singular or plural), which also explains a tag after tapping its button, and the `<dialog id="glossary">` with every word A–Z ("See all the words"), each with "Find plays" (a search for the word) when a play is tagged with it. The global keyboard shortcuts are off while the dialog is open. A missing or broken glossary just hides all three.
- Layout: `.wrap` is a two-column grid. The left `.library` panel (title, search, level filter, path picker, word card, play list, and under the list "Surprise me" plus a "Draw a play" link to the editor) is sticky and fills the window height, and its list scrolls vertically; the right `.content` column holds the court and play info (side by side above 1240px, stacked below). Under 880px the panel becomes a normal block on top and the list turns into a sideways-scrolling chip row. `revealChip()` scrolls the list (either direction) to the selected play without moving the page.
- Inbound plays: the player holding the ball in frame 0 may stand off the court (`pointError` in `playbook.js` allows x -40..540, y -40..470; `onCourt()` is the real court). `tools/build.js` enforces that only that inbounder is ever off the court and never steps back out. `frameCourt()` in `app.js` widens the SVG viewBox on any side where someone stands out of bounds (players are 26 units from the edge), so normal plays keep the original `-14 -14 528 498` view; speech bubbles clamp to the current view.
- `editor.html` + `js/editor.js` + `css/editor.css`: the play editor. Drag players per step (snaps to spot names within 9 units; dragging back to the previous spot removes the move), drag a ◆ handle to curve a path (tap it twice to straighten; double taps are detected in `pointerdown` because the court redraws between clicks), edit ball/question (`ask` or `where`)/screens/bubbles/caption per step and the play's fields, preview with a scrubber, and copy or download `formatPlay` output. Drawing uses a cleaned-up copy (`drawable`/`safeBall`) so half-finished edits still render; checks run `checkPlay` then `lintPlay` on the real play. Nothing is stored in the browser; a `beforeunload` prompt guards unsaved work.
- Link previews: `index.html` has `og:`/Twitter tags with absolute `https://karthikpds.github.io/hoops/` URLs (crawlers need them, so a fork must change them). Crawlers don't run JS, so every `#play` link shares the same card. The picture, `img/share.png`, is a screenshot of `tools/share-image.html` (which draws a real play with `renderCourt`); the command to remake it is in that file.
- `tools/build.js`: `checkPlay` plus `lintPlay`: only the inbounder may be off the court, caption chips must refer to cast members, bubbles ≤ 16 chars (warning), handoff players within 50 units at their closest (warning), an `ask` answer should be the most open teammate without the ball when the question pops up (warning), a `where` player must move more than `WHERE_RADIUS` + 10 so a tap on them doesn't count, and an overlap sweep of every step at t = 0, 0.05 … 1 that fails if two players get closer than 26 units. Then `checkPaths` on `plays/paths.json` (every id must be a play file), `checkGlossary` on `plays/glossary.json`, and a warning for every tag that no glossary word covers. Keeps the existing order of `index.json`, drops removed plays, and slots new ones in after the last play of the same or easier level. Prints `::error file=…::` annotations under GitHub Actions.

## How the court and animation work

- SVG half court, `viewBox="-14 -14 528 498"`, 10 units = 1 ft. Baseline at y=0 (top), basket at (250, 52.5), half-court line at y=470. Three-point arc radius 237.5; corner threes are x<30 or x>470 when y<142.
- Players are circles of radius 17: blue offense `o1`..`o5`, red defense `d1`..`d5` (labelled X1..X5). The ball is drawn above the players.
- Timeline: `p` is a continuous position. 0 is the setup, integer k is the end of step k. `tick()` advances `p` (with a hold between steps while playing); `render()` draws everything from `p`. `tick()` snaps `p` to the step end when within 1e-9: without that, regular 60 Hz frame times can leave `p` at 3.9999999999999996, `k` overshoots the last frame, and the loop dies.
- Movement lines use playbook notation and are generated automatically: solid arrow = cut, zigzag = dribble, dashed orange = pass, line with a T end = screen, two short orange bars = handoff. Earlier steps stay faded on the court. Defenders' moves are only drawn (in red) in a defense play (`"side": "defense"`), which also flips the legend text and shows a note in the info panel.
- Ball actions: hold, dribble (optional `cross`: a crossover, the ball bounces low across the front of the body to the other hand early in the step, and stays there), fake (a shot fake: the ball goes up about 30 units and back down in the first 60% of the step, and the holder keeps it; no line is drawn), pass (optional bounce, or lob: the ball flies about 60 units high and its line bows out, `lobBend`), handoff (the ball moves between hands in a short window around `handoffT`), shot (made: last step, celebration), shot with `miss` (flies to the rim, then pops off to `missAt`), and rebound (from `missAt` to the rebounder, then "Rebound!"). Possession (`teamWithBall(frames, k)` in `playbook.js`): blue has the ball until a red player grabs a rebound, then red can hold, dribble, pass and hand off (never shoot or fake: red's basket is at the far end), and a blue rebound gives it back. `checkPlay`, the `ask` lint, the page's questions and the editor's menus all follow it, and red's moves get lines whenever red has the ball. `scr` pairs may be `[defender, player]` for a box out. The ball sits at `handG(q, side)`, 12 units to the holder's right or left; `side` comes from `play.hand`, which only a crossover flips, and a pass, handoff, shot or rebound puts the ball back in the new holder's right hand.
- Controls: play/pause, step back/next, restart, clickable step dots, speed, show/hide defense and lines, "Questions" on/off, read aloud, follow, print. Keyboard: `/` focuses search, Space plays/pauses, Left/Right step, 1-5 answer a "Who's open?" question. Shortcuts are ignored while typing in an input. In search, Enter opens the top result and plays it; Escape clears.
- "Next play" moves through the current search results when there are several, otherwise through the whole library. "Surprise me" picks a random play from the same pool, never the one showing.
- Read aloud (off by default, hidden without `speechSynthesis`): every new caption is spoken (`{1}` → "1", `{X1}` → "X 1"). While playing, `tick()` holds the next step until the voice finishes; `speakUntil` is a length-based safety net because some browsers never fire `onend`.
- Follow: the row under the controls (or a tap within 30 units of a player on your team, when no question is up) picks one player; everyone else gets `.dim` and their lines fade (`stepPaths(play, j, follow)`). Cleared when the play changes and ignored while a question is up.
- Print: the 🖨️ button (and the `beforeprint` event, so Ctrl+P works too) fills `#printSheet` with `renderCourt` for every frame plus captions and notes; `@media print` hides everything else and lightens the court.
- Questions (on by default, `quizOn`, the "Questions" toggle): when the timeline is about to start a step whose frame has `ask` or `where` and that step hasn't been answered yet, `tick()` calls `startAsk()` right as the step before ends (no hold). `quiz` holds the question, with `kind` "who" (`ask`) or "where" (`where`); Play and Next are disabled, the dots are swapped for the question row, bubbles are hidden, and the caption shows the question or hint. The right answer or "Show me" adds the step to `answered`, then resumes the way the play was going (playing or stepping) after 1.2 s. Restart, Again and picking a play clear `answered`; Back and the dots drop the question without answering it.
  - "Who's open?" (`ask`): about the team with the ball (`quiz.team`, red after a red rebound): one button per player on that team (red ones read X1…), a tap anywhere within 48 units of one of them picks the nearest (`tapCourt`), as do keys 1-5. The court gets `.asking` (blue) or `.asking-d` (red).
  - "Where should 2 go?" (`where`, a player on your team who moves this step): the court gets `.placing` and the player `.mover` (a pulsing yellow ring). A tap within `WHERE_RADIUS` (60) of where that player ends the step is right (`answerSpot`): a green ring marks the spot and the player runs into it. A miss leaves a red x and a hint: the player standing there, or closer to/farther from the hoop, or more to the left/right. A `where` about a defender is skipped while the defense is hidden. No keyboard answer: "Show me" is the way through.

## Adding or editing a play

The file format, spot names and checks are documented for humans in `plays/README.md`; read it before writing a play.
In short: `{ name, emoji, level (1-3), side?, tags?, idea, why, tryit, cast, frames }`, frame 0 is the setup, each frame has
`pos`, `ball`, optional `ask` (the open player, on the step that passes to them) or `where` (a player on your team who runs somewhere this step), `scr` and `bub`, and `say`. The editor
(`editor.html`) can write the file, but check it the same way. Then:

1. Write `plays/<kebab-case-id>.json` (`index`, `paths`, `glossary` and `bundle` are taken). Positions can be spot names (`TOP`, `LS`, `RS`, `LW`, `RW`, `LC`, `RC`, `LE`, `RE`, `HP`, `LB`, `RB`), `[x, y]`, or `[x, y, cx, cy]` for a curve.
2. Run `npm run build` and fix everything it reports. Overlaps are the usual problem: curve paths around players and keep everyone ~34 apart.
3. Preview it (`npm start` or the `hoops` launch config), open `#<id>`, and watch every step at normal speed.
4. Add it to a learning path in `plays/paths.json` if one fits, and give any new tag a glossary word (the build warns until you do).

## Conventions

- Kid-friendly copy: short sentences, sentence case, no all-caps labels. Bubbles are a word or two.
- Theme colors are CSS tokens on `:root` with dark-mode overrides; court colors are tokens too.
- No frameworks, no bundler, no npm dependencies, and nothing about the user is ever stored in the browser (no localStorage, no cookies). The only stored thing is `sw.js`'s copy of the site's own files. Keep `js/playbook.js` and `js/court.js` free of DOM code.
- Play files are written in `formatPlay`'s layout (the tests enforce it), so a hand edit should keep keys in the standard order: `name, emoji, level, side, tags, idea, why, tryit, cast, frames` and `pos, ball, ask, where, scr, bub, say`.
- Text from play files is escaped before it goes into `innerHTML` (`esc()` in `app.js`); keep it that way for any new field.
